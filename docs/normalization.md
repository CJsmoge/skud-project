# Нормализация

## 1НФ (Первая нормальная форма)

**Проверка:** все атрибуты атомарные, нет повторяющихся групп, есть PK.

| Сущность | Проверка | Результат |
|---|---|---|
| Employee | Атомарные атрибуты | ✅ |
| Card | Атомарные атрибуты | ✅ |
| Zone | Атомарные атрибуты | ✅ |
| AccessLevel | Атомарные атрибуты | ✅ |
| Request | Атомарные атрибуты | ✅ |
| Controller | Атомарные атрибуты | ✅ |
| StatusHistory | Атомарные атрибуты | ✅ |

**Вывод:** 1НФ выполнена.

## 2НФ (Вторая нормальная форма)

**Проверка:** нет частичных зависимостей от составного PK.

**Составных PK нет** — у всех сущностей первичный ключ = `id` (одиночный). Частичные зависимости невозможны.

**Вывод:** 2НФ выполнена.

## 3НФ (Третья нормальная форма)

**Проверка:** нет транзитивных зависимостей (неключевой атрибут не зависит от другого неключевого).

| Сущность | Проверка | Результат |
|---|---|---|
| Employee | department, position, phone, email зависят только от id | ✅ |
| Card | employee_id, number, status, issued_at, blocked_at зависят от id | ✅ |
| Zone | name, description, level_id зависят от id | ✅ |
| AccessLevel | name, description зависят от id | ✅ |
| Request | employee_id, card_id, zone_id, controller_id, event_time, direction зависят от id | ✅ |
| Controller | zone_id, name, location, is_active зависят от id | ✅ |
| StatusHistory | card_id, old_status, new_status, changed_at зависят от id | ✅ |

**Особое внимание:** `Zone.level_id` — это FK на `AccessLevel`, нормальная связь между сущностями, а не транзитивная зависимость.

**Вывод:** 3НФ выполнена. Нарушений не обнаружено.

## Внесённые изменения

**Изменений не требовалось** — модель изначально соответствует 3НФ.

**Опционально (не в MVP):** можно вынести `department` в отдельный справочник `Department`, если отделов станет много. Для текущего объёма данных это избыточно.

## Итог

Модель данных СКУД соответствует **3НФ**:
- ✅ 1НФ — все атрибуты атомарные.
- ✅ 2НФ — нет частичных зависимостей.
- ✅ 3НФ — нет транзитивных зависимостей.
